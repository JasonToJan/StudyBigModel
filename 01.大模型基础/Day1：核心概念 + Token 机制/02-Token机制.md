# 02. Token 机制：模型眼里没有文字，只有数字

> Day1 学习笔记 · 第二篇（今日重点）｜ 阅读时间约 15 分钟
> 目标：读完这篇，你能解释"模型为什么不认识字"、算出一篇文档大概烧多少钱、说清上下文窗口超限会发生什么。

---

## 一、先说结论：模型眼里没有文字，只有数字

上一篇我们说模型是"超级接话机器"，负责预测下一个字。但你有没有想过一个问题：

**模型是一个跑在显卡上的神经网络，它处理的只能是数字。** 它根本没见过"你"、"好"、"hello"这些字符——就像计算器不认识"亿"这个汉字，只认识数字。

所以，在你按下回车到模型开始思考之间，发生了一次"翻译"：

```
你的文字 ──[Tokenizer 分词]──> token 序列 ──[查表]──> 数字序列 ──> 模型开始干活

"我爱AI" → [我][爱][AI] → [30214, 12853, 1557] → 模型眼里就长这样
```

> 🔑 核心认知：**模型眼里没有文字，只有 token 序列。** 一切成本、速度、上下文限制，都是按 token 算的，不是按"字"算的。

---

## 二、什么是 Token：介于"字"和"词"之间的碎片

Token 是模型处理文本的最小单位。注意，它**不是**字，**也不是**词，而是介于两者之间的碎片：

| 原文 | 可能的切分 | token 数 |
|---|---|---|
| 人工智能 | 人工 + 智能 | 2 |
| 吃了吗 | 吃 + 了吗 | 2 |
| unbelievable | un + believ + able | 3 |
| Hello, world | Hello + , + world | 3（标点也算） |

几个容易惊讶的事实：

- **空格和标点都是 token**。一段代码里大量的 `{` `}` `(` `)` 会悄悄吃掉很多 token
- 常见词是 1 个 token（"的"、"the"、"人工智能"里的高频组合），生僻词会被拆成碎片
- 切分规则不按"语义"来，而是 tokenizer 训练时统计出来的"高频组合表"——它只管省钱（token 越少，模型算得越快），不管这个碎片对人类有没有意义

类比：tokenizer 像一个**只认常用偏旁部首的快递打包员**——"显示器"整箱发货（1 个 token），"魑魅魍魉"这种生僻货就拆成四个盒子逐个寄。

---

## 三、Tokenizer：文本与数字之间的翻译官

Tokenizer（分词器）的工作就是双向翻译：

1. **进入模型前**：文字 → token → 每个 token 查一张固定的大表（词表，通常十几万行），换成它的编号（token id）
2. **模型输出后**：模型吐出一个编号 → 反查表 → 变回文字给你看

模型从头到尾只会处理编号。"预测下一个字"的精确说法是：**预测词表里哪个编号的概率最大**。

一个工程细节（后面学微调/部署时会再遇到）：**tokenizer 和模型是配套的**。Qwen 的 tokenizer 和 GLM 的 tokenizer 词表不同，同一个词在不同模型里的编号也不一样。所以"用 Qwen 的 tokenizer 去数 GLM 要消耗的 token"只能算估算，不是精确值。

---

## 四、中文 vs 英文：为什么中文更"贵"

这是直接影响你做产品成本的知识点，务必记住结论：

| 语言 | 经验值 | 原因 |
|---|---|---|
| 英文 | 1 个词 ≈ 1 token | 主流 tokenizer 的训练语料以英文为主 |
| 中文 | 1 个字 ≈ 1~2 token | 很多中文字/词不在高频表里，要拆碎 |

**同样表达一个意思，中文往往消耗更多 token，也就更烧钱、更占上下文窗口。**

快速估算口诀（做需求评估时很够用）：

- 500 字中文 ≈ **500～1000 token**
- 500 词英文 ≈ **500 token 左右**
- 一段代码的 token 数，往往比看起来多得多（符号+缩进都算）

好消息：国产模型（Qwen、GLM、DeepSeek）的 tokenizer 专门优化过中文，同样一段中文比 GPT 系列消耗的 token 更少——这也是我们技术栈选国产模型的原因之一。精确测量不用背口诀，直接用工具：OpenAI 官方 tokenizer 可视化页（platform.openai.com/tokenizer），或各国产平台控制台的 token 计数器。

## 五、上下文窗口（Context Window）：模型的"桌面大小"

### 1. 它是什么

模型一次能"看到"的 token 总量上限，叫上下文窗口。

类比：模型像一个坐在**固定大小桌子**前的会计。

- 每轮对话，你要把**历史全部记录**重新摆到桌上，它才能"记得"之前说过什么
- 桌子一旦摆满，要么摆不下（报错），要么你主动把最早的记录**从桌上收走**（早期的对话内容被截断）

### 2. 关键点：输入和输出共享这张桌子

很多人以为"我的 prompt 没超就行"，错。共享窗口里包括：

```
上下文窗口总容量 = 系统提示词 + 历史对话 + 当前问题（输入）
                 + 模型正在生成的回答（输出）
```

输入塞得越满，留给回答的空间就越小。做应用时如果用户问题很短但历史很长，模型可能只蹦出几个字就被"桌子边缘"掐断了。

### 3. 超限会发生什么（工程上必须处理）

| 情况 | 表现 |
|---|---|
| 输入本身超限 | API 直接报错（最常见） |
| 输入接近上限 | 平台帮你截断**最早的内容** → 模型"忘了"开头的约定，行为突变 |
| 输出空间不够 | 回答写到一半戛然而止（`finish_reason=length`） |

这就是为什么后面的课程要学**对话历史管理**：不能无脑把所有历史都塞回去，要做摘要、裁剪、滑动窗口。现在只需记住现象。

### 4. 一个反直觉点：模型其实"没有记忆"

第一篇说过模型原生无记忆。网页版 AI 之所以"记得"你上一句，是因为**产品每次都把完整历史重新发给了模型**。记忆的感觉 = 历史对话被塞进上下文窗口。窗口是有限的，这就是一切"记忆管理"问题的源头。

## 六、Token 与钱：看懂 API 账单

API 按 token 计费，返回结果里有个 `usage` 字段：

```json
"usage": {
  "prompt_tokens": 1520,       // 你发过去的（输入）
  "completion_tokens": 380,    // 模型生成的（输出）
  "total_tokens": 1900         // 总计
}
```

三个工程常识：

1. **输出比输入贵**（通常贵 2~5 倍）。让模型"少废话"不只是体验问题，是真金白银
2. **多轮对话下输入成本滚雪球**：第 10 轮对话，要把前 9 轮历史全部重新计费一遍——长对话越聊越贵
3. 缓存命中（prompt caching）：重复的前缀（如固定的系统提示词）可以按大幅折扣计费，做产品时值得了解

粗略感受一下量级：按主流国产模型定价，100 万 token 的输入大约几元人民币——个人学习和原型开发，成本通常低到可以忽略；但产品放量后，token 成本会成为核心优化指标。

---

## 七、本篇小结

1. 模型眼里没有文字，只有 **token 序列**；Tokenizer 负责文字 ↔ 数字互转，且与模型配套
2. Token 是介于字和词之间的碎片，**空格标点都算**；中文 1 字 ≈ 1~2 token，比英文更"贵"
3. 上下文窗口 = 输入（系统提示 + 历史 + 当前问题）+ 输出**共享**的总容量；超限会报错、截断或答到一半掐断
4. 模型的"记忆"其实是历史对话被反复塞回窗口——窗口有限，所以记忆必须管理
5. API 按 token 计费：输出贵于输入，多轮对话输入成本滚雪球
