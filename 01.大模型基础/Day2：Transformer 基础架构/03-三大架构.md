# 03. 三大架构：同一套积木的三种拼法

> Day2 学习笔记 · 第三篇 ｜ 阅读时间约 12 分钟
> 目标：读完这篇，你能给任意一个常见模型归类（Encoder-only / Encoder-Decoder / Decoder-only），并讲清为什么主流 LLM 全是 Decoder-only。

---

## 一、先说结论：积木只有一套，拼法有三种

上一篇的流水线里有一个"可拆装"的开关：**注意力允许看哪边的词**。

- **Encoder（编码器）**：只管"读"——把输入加工成充分理解的表示，**不负责生成文字**
- **Decoder（解码器）**：只管"写"——接 Day1 的自回归，逐 token 往外蹦

拿这两个半件当积木，得到三种拼法：

| 拼法 | 结构 | 擅长 | 代表 |
|---|---|---|---|
| Encoder-only | 只要"读" | 理解类：分类、检索、语义匹配 | BERT、bge 系列 |
| Encoder-Decoder | 读 + 写 | 输入输出对齐的序列任务：翻译、摘要 | T5、Whisper |
| Decoder-only | 只要"写" | 生成类：对话、写作、代码 | **GPT、Qwen、GLM、DeepSeek（主流 LLM 全在这）** |

下面逐个认识，最后回答"为什么独宠第三种"。

---

## 二、Encoder-only：只读不写的"审稿人"

代表：BERT（Google, 2018）。

**特点**：看文本的方式是**双向**的——处理每个词时，左边右边的词全都能看（全员开会，名正言顺）。所以"理解"能力极强。

但它**天生不会生成**：没有自回归出口，你不能让它"接着往下写"。它读完文本的产出是每个词的"深度理解向量"，不是一段话。

**擅长的活**（判断题、选择题型的任务）：

- 情感分类：这条评论是好评还是差评？
- 文本匹配：这两句话是不是一个意思？
- **语义向量检索**：把文本变成"语义地图坐标"，供搜索用——现在最火的 bge/gte 系列 embedding 模型都源自这条路线

类比：一个目光锐利的**审稿人**，读得又快又准，但你让他现场写小说，他不会——他这辈子的工作是"读"。

> 别以为 Encoder-only 过时了。RAG 系统里的"检索半边"靠的就是它，而且又小又便宜。

---

## 三、Encoder-Decoder：一读一写的"同声传译"

代表：T5；**2017 年那篇原版 Transformer 论文，本身就是为机器翻译设计的这个结构**。

**工作方式**：两个半件接力——

```
Encoder 读入："今天天气真好" → 加工成理解向量
                    ↓
Decoder 输出："The weather is really nice today"（逐 token 自回归生成）
```

**擅长的活**：输入和输出都是序列、且对应关系明确的任务——翻译、语音识别（Whisper）、摘要。

**为什么没能统治 LLM**：它的前提是"任务边界清晰、输入输出成对"。但真实世界的生成任务五花八门——写邮件、编代码、续写小说、闲聊——很难都硬套进"固定输入模板 → 固定输出模板"的模具。灵活性输了。

类比：**同声传译**，读入和输出严格配对，专业高效，但你让他即兴主持一档脱口秀，就超纲了。

---

## 四、Decoder-only：只出不进的"接龙大师"

代表：GPT 起家，如今 Qwen、GLM、DeepSeek、Claude……**你叫得上名字的对话大模型几乎全是它**。

**特点**：只有 Decoder 半件，看文本是**单向**的——每个 token 只能看它前面的词，看不到后面的（这叫**因果掩码**：不许偷看答案）。

为什么这样设计？因为它是为 Day1 的**自回归接龙**量身定做的：

- 预测第 N 个 token 时，本来就该只看前 N−1 个——"偷看后面"反而作弊且没意义
- 结构和任务**严丝合缝**，一个字都不浪费

**万物的统一：什么任务都能变成"接龙"。**

| 传统眼光 | Decoder-only 眼光 |
|---|---|
| 问答 | 给我一段"问：… 答："，请续写答案 |
| 翻译 | "英文：… 中文："，请续写中文 |
| 写代码 | "注释写着求质数，请续写函数实现" |
| 闲聊 | 全部历史连起来，请续写下一句 |

类比：一个**续写大师**，你给他任何开头，他都能接下去——只要把任务包装成一个"开头"。

---

## 五、本课重点：为什么主流 LLM 独宠 Decoder-only

四个原因，按重要性排：

1. **万物皆可接龙（任务统一）**：不管什么任务，都变成"给个开头请续写"。训练时不需要给数据打任务标签——互联网上的**一切文本本身就是现成训练题**（任何文本的下一个词天然就是标准答案）。数据获取成本几乎为零，这在"大力出奇迹"时代是决定性优势。

2. **和自回归严丝合缝**：生成类应用（对话、写作、代码）的本质就是从左到右逐 token 输出，单向注意力完全够用，双向那一半是白花钱的算力。

3. **结构更简单 = 规模化友好**：少半个结构，同样的算力能堆更多层数据、跑更快的训练。

4. **规模化的实战验证**：GPT-3 把这条路 scale 到 175B 后展现了惊人的"涌现能力"，全行业目睹后纷纷跟进，生态、工具、优化全部围绕它积累——马太效应锁定胜局。

> 🔑 一句话：**Decoder-only 赢在"任务统一 + 数据白嫖 + 结构简单 + 已被验证"，不是因为它"理解力最强"。**

**但注意别学偏**：不是 Encoder-only 被淘汰了。做 RAG 时你会**同时用到两种**——Encoder-only 的 embedding 模型负责检索（又快又便宜），Decoder-only 的 LLM 负责生成回答。它们是搭档，不是替代关系。

---

## 六、工程落点：你以后什么时候用哪种

| 场景 | 选谁 |
|---|---|
| 对话 / 写作 / 代码生成 | Decoder-only 对话模型（Qwen / GLM / DeepSeek） |
| 语义检索 / RAG 的召回 | Encoder-only embedding 模型（bge 系列） |
| 海量文本打标签、意图分类（要省钱） | 小型 BERT 类模型，比调大模型便宜几个量级 |
| 语音转文字 | Whisper（Encoder-Decoder） |

---

## 七、本篇小结

1. 三种拼法：**Encoder-only（只读，理解）/ Encoder-Decoder（读+写，配对任务）/ Decoder-only（只写，生成）**
2. 关键区别在注意力方向：Encoder **双向**（理解力强），Decoder **单向**（不许偷看，配自回归）
3. LLM 独宠 Decoder-only 的四理由：**任务统一、数据白嫖、结构简单、已验证**
4. Encoder-only 没死：embedding / 检索仍是它的天下，RAG 里两种架构是搭档
