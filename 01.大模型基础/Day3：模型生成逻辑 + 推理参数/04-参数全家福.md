# 04. 参数全家福：max_tokens、stop、penalty、seed、stream 一次认全

> Day3 学习笔记 · 第四篇（收官）｜ 阅读时间约 12 分钟
> 目标：读完这篇，你能看懂任意一家平台的 API 参数表，知道每个参数管什么、什么时候用、经典踩坑在哪。

---

## 一、先说结论：剩下的参数分四类

temperature 和 top_p 之外，API 参数表里的常客其实只干四件事：

| 类别 | 参数 | 一句话 |
|---|---|---|
| **何时停** | max_tokens、stop | 给回答设天花板、设"闭嘴暗号" |
| **防复读** | repetition_penalty / frequency_penalty / presence_penalty | 治"复读机" |
| **可复现** | seed | 把随机过程存档 |
| **交付方式** | stream | 一口气给完 vs 逐字推流 |

逐个认领。

---

## 二、max_tokens：天花板，不是目标

**作用**：限制本次回答最多生成多少 token，到量就掐断（对应第一课的 `finish_reason=length`）。

三个必须建立的认知：

1. **它是保险丝，不是"生成得越多越好"的设置**。设它的目的是防止失控输出，不是为了"要长答案"
2. **设大了不浪费钱**——只按实际生成的 token 计费，上限只是"最多允许说多少"。但会拉长单次请求的最坏耗时
3. **设小了会出事故**——最经典的坑：让模型输出 JSON，结果在半截被掐断 → 下游解析直接报错

> 🔧 经典踩坑现场：JSON 抽取任务莫名解析失败 → 查了半天 prompt → 其实是 `max_tokens` 给了 512，结果在第 30 个字段处被 `length` 掐断。**先看 finish_reason，再怀疑 prompt。**

---

## 三、stop：自定义"闭嘴暗号"

**作用**：指定一个（或几个）字符串，生成过程中一旦出现就立刻停止，且这段暗号本身通常不计入输出。

最常见的用法：**防止模型"替你把下一句话也说了"**。

老派对话系统的做法是把历史拼成一段文本让模型续写：

```
用户：退货流程是什么？
助手：您可以在订单页申请……
用户：            ← 模型自问自答，把"用户"的下一句也编出来了
```

解法：设 `stop: ["用户："]`——一写到这个暗号就闭嘴，正好停在助手该停的位置。其他常用场景：代码生成时遇到 "```" 就停、抽取任务遇到换行就停。

现在各家对话接口已内置了聊天格式，这个技巧平时用不上了，但**在你以后做续写式应用、或用基座模型时（Step10 微调后部署），它是保命技巧**。

---

## 四、复读机三兄弟：三种惩罚参数

先回忆 Day1 的结论：自回归机制下，已生成的 token 会不断"自我强化"——一旦开头重复，后面越滚越凶。惩罚参数就是官方给的解药。

三者（不同平台叫法和支持度不同，见名知义即可）：

| 参数 | 逻辑 | 类比（点菜） |
|---|---|---|
| **presence_penalty** | 只看"出现过没有"：出现过的 token，惩罚一次 | 点过的新菜，下次再加钱——鼓励**开新话题** |
| **frequency_penalty** | 看出现次数：出现越多，惩罚越重 | 重复点同一道菜，越点越贵——压制**重复用词** |
| **repetition_penalty** | 对已出现 token 整体打折（开源社区 / GLM 系常用） | 吃过的菜统一涨价 |

**用法与分寸**：

- 出现复读苗头（卡在同一句话循环）→ 先小幅调 frequency_penalty（0.2~0.5 起步）
- **千万别调过头**：惩罚太狠，模型会"刻意绕开"某些关键词，输出开始吞字、换词、变得诡异——质量反而崩了
- **需要重复的场景禁用**：代码（变量名反复出现）、JSON（key 固定）、术语解释——这些任务里"重复"是刚需，开惩罚等于拆台

---

## 五、seed：把随机过程存档

**作用**：固定随机种子。配合低温，可以做到"同样输入 → 几乎逐字相同的输出"。

什么时候用：

- **调试**：问题复现后固定 seed，确保每次看的是同一个现象，而不是每次都在掷新骰子
- **评测对比**：改了 prompt 想对比效果，固定 seed 排除随机干扰
- **产品**："重新生成"功能如果要求和上次一致（少数场景）

温度不为 0 时，seed 只是让"抽签顺序"固定，不是让模型变笨或变聪明——它只管复现。

---

## 六、stream：交付方式开关

Day1 第三课埋过的伏笔，正式收下：

- `stream=False`（默认）：等全部生成完，一次性返回完整结果——**批处理、数据流水线用这个**，方便程序处理
- `stream=True`：逐 token 推送，打字机效果——**面向用户的产品对话必开**（首 token 延迟决定体验生死线）

一个容易忽略的点：流式模式下 `usage` 字段（token 消耗统计）默认可能不返回，计费统计逻辑要注意各家文档说明。

## 七、参数速查卡（存下来当手册用）

| 参数 | 管什么 | 常用值 | 经典踩坑 |
|---|---|---|---|
| temperature | 分蛋糕的贫富差距 | 严谨 0~0.3 / 创意 0.8~1.2 | 误当"智力旋钮" |
| top_p | 谁能上桌 | 保持默认 0.9~1.0 | 和温度同时拧到极端 |
| max_tokens | 输出天花板 | 留足余量 | JSON 被掐断解析失败 |
| stop | 闭嘴暗号 | 续写场景必备 | 暗号选得太平常，提前误停 |
| penalties | 防复读 | 0.2~0.5 起步 | 调过头绕关键词；代码任务误开 |
| seed | 复现 | 调试评测时固定 | 以为它影响能力 |
| stream | 交付方式 | 产品对话必开 | 忘了流式下 usage 的坑 |

## 八、Day3 全篇总结（四篇串起来）

1. **01 生成逻辑**：模型给概率表，采样策略决定挑哪个；贪心 vs 采样是两极
2. **02 temperature**：在候选池里**分蛋糕**——低温赢家通吃，高温众生平等
3. **03 top_p / top_k**：在分蛋糕前**圈定谁能上桌**——动态名额的 top_p 是现代默认
4. **04 本篇**：何时停（max_tokens / stop）、防复读（penalties）、可复现（seed）、交付（stream）

> Day3 一句话：**API 的生成参数，就是对"概率表 → 文字"这最后一公里的精细化遥控。** 从明天起，我们转向"模型出厂前"的故事——模型是怎么被调教得这么听话的。
